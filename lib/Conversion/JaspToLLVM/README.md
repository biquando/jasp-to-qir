# JaspToLLVM Pass

This pass converts the Jasp-dialect types and operations into LLVM-dialect,
matching the Quantinuum QIR spec. It also unwraps rank-0 tensors generated by
Jasp into their scalar values.

- **Input:** MLIR with jasp/func/scf/math/arith/tensor dialects. This should
  have been generated with `jaspr.to_mlir(lower_stablehlo=True)`.
- **Output:** MLIR with llvm/func/scf/math/arith dialects.

## Configuration

This pass exposes two options:

| Option | Default | Description |
| ------ | ------- | ----------- |
| `resource-management` | `static` | Selects static resource IDs or dynamic allocation of qubits and results. The other option is `dynamic`. |
| `result-buffer-size`  | `64`     | In dynamic mode, the size of the resource buffer must be statically-determined. This option is that size, and represents the maximum bitsize of a measurement. |

## Module analysis

In static mode, each `jasp.create_qubits` operation must specify a constant
number of qubits. The pass can then assign that number of qubits, addressed as a
range of integers. For example, if `m` qubits have already been assigned and we
want to create a new array of `N` qubits, then we give them integer addresses
`[m,m+N)`.

The pass also walks through the module and records QIR attributes based on:
- the selected resource-management mode
- static qubit and result requirements
- whether the program uses helper functions, backward branches, multi-target
  branches, multiple entrypoint returns, or floating-point operations

## Qubits

In QIR, qubits are represented by opaque `ptr` types. We represent qubit arrays
differently depending on the resource management mode.

#### Static allocation

In static mode, we use `QubitArray {base: i64, size: i64}`. The base index and
size are determined during module analysis. The pass fails if they cannot be
determined statically.

Array slicing is implemented by creating a new `QubitArray` with a base and size
corresponding to the slice. Array fusing is not supported.

#### Dynamic allocation

In dynamic mode, we use `QubitArray {array: ptr, size: i64}`. `QubitArray.array`
is allocated with `alloca ptr, i64 %size, align 8`. Each qubit in the array is
then allocated individually with `@__quantum__rt__qubit_allocate` and stored in
the array in an scf for loop. We don't use the
`@__quantum__rt__qubit_array_allocate` because Quantiuum QIR doesn't support a
dynamic array size (although
[documentation](https://github.com/Quantinuum/qir-qis/blob/main/qtm-qir-reference.md#dynamic-allocation-and-arrays)
only states that dynamically-sized *classical* buffers are not supported).

Array slicing is implemented by creating a new `QubitArray` whose `array` field
points to an element inside of the original array. Array fusing is implemented
by copying the qubit `ptr`s inside the two arrays into a new array.

See [docs/allocation.md](/docs/allocation.md) for a more detailed description of
how we do dynamic qubit array allocation.

## Results

During module analysis, each syntactic measurement is assigned a non-overlapping
range of integers.

- In static mode, the range corresponds to the indices of the result slots used
  for that measurement, which must be determined statically. For example, if 20
  result slots have already been allocated, then a new 5-qubit measurement will
  be assigned the range `[20, 24]`.
- In dynamic mode, the range consists of only a single integer.

For now, every measurement result is outputted. The starting number `N` in each
range `[N, M]` is used in the output label, i.e. `result_N`.

Since Quantinuum's QIR does not support array measurement, we must emit
`@__quantum__qis__mz__body` for each qubit in the array. The details of how
array measurement is performed depends on the resource management mode.

#### Static measurement

A compile-time for loop iterates through every qubit and result index. Then
left-shifts and ORs are used to pack the results into an `i64`.

#### Dynamic measurement

In dynamic mode, we use a single statically-sized result buffer, which is
allocated at the beginning of the main function. We then create a global alias
for the buffer, which can be access from any function. Then every array
measurement uses an scf for loop to write measurement results into the buffer
through the global alias. Then left-shifts and ORs are used to pack the results
into an `i64`.

## Quantum gates

We use the following Jasp $\to$ QIR gate translation.

| Jasp gate | QIR declaration |
| --------- | --------------- |
| `h`, `x`, `y`, `z`, `s`, `t`, `rx`, `ry`, `rz`, `cz` | `@__quantum__qis__*__body` |
| `s_dg`, `t_dg` | `@__quantum__qis__*__adj` |
| `p` | `@__quantum__qis__rz__body` |
| `cx` | `@__quantum__qis__cnot__body` |

## Scalarization

Jasp wraps scalar values in rank-0 tensors, which must be unwrapped before
converting to QIR. For a scalar element type `T`, we apply the following three
transformations:

- `arith.constant dense<value> : tensor<T>` becomes `arith.constant value : T`
- `%scalar = tensor.extract %tensor[] : tensor<T>` is removed, and uses of
  `%scalar` are replaced with the converted scalar value of `%tensor`
- `%tensor = tensor.from_elements %value : tensor<T>` is removed, and uses of
  `%tensor` are replaced with `%value`
